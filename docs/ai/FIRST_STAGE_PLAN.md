# План первого этапа разработки

Статус: одобрен 2026-10-03 и реализован 2026-10-04. Фактическое состояние — в [CURRENT_STATE.md](CURRENT_STATE.md).

## 1. Карта сайта и граница этапа

Полная карта из ТЗ: `/`; `/solutions/{radar,integrations,ai,marketplaces}`; `/industries/{wholesale,manufacturing,services,marketplaces}`; `/1c`; `/cases`; `/approach`; `/about`; `/contact`.

В первом этапе реализуются только `/`, Header и Footer. Навигация на ещё не созданные страницы не должна вести на пустые маршруты: до их реализации её пункты могут вести к соответствующим секциям главной. CTA «Показать свой процесс» направляется к рабочему способу связи, который будет определён перед реализацией; не создаём видимость работающей отправки без backend.

## 2. Содержание главной

1. Hero с формулировкой из раздела 56 ТЗ, двумя CTA и адаптивной схемой потоков 1С ↔ другие системы ↔ Radar.
2. «Узнаёте свой бизнес?» — конкретные ручные операции и поздние финансовые сигналы, с приоритетом на читаемость вместо однотипной сетки из восьми карточек.
3. Блок о совместной работе 1С и остальных систем и четыре направления работы. Текущий заголовок: «Поможем 1С и остальным системам работать вместе».
4. Большой блок `Altacod Radar`: обзор сигналов, выбранное событие, причина, влияние на показатель и возможное действие. Все данные подписаны как демонстрационный сценарий.
5. Блок 1С как ядра учёта с понятной схемой расширения и интеграций.
6. Блок ИИ «под капотом» с разделением детерминированного расчёта, прогноза и интерпретации; без обещаний, что LLM считает финансы.
7. Краткий процесс работы и финальный CTA.

## 3. UI-макет Radar

Предлагается интерактивный интерфейс продукта, а не декоративный скриншот: список из трёх сигналов, переключение выбранного события, детали причины и краткое предлагаемое действие. Один сценарий заказа может позволять менять скидку и показывать пересчёт маржи по явной детерминированной формуле; пользовательский ввод и полученный результат будут промаркированы как демо. На мобильном список и детали складываются вертикально, цифры остаются крупными и читаемыми. Анимации только дополняют состояние и отключаются по системной настройке уменьшения движения.

## 4. Дизайн и компоненты

- Базовые токены: светлый фон `#F7F8FA`, белые поверхности, тёмный текст, холодный синий `#3157E2`; amber/red только для предупреждений. Итоговые оттенки проверяются на контраст WCAG AA.
- Шрифт Inter либо Geist; шкала desktop: H1 56–72 px, H2 36–48 px, основной текст 16–18 px. Контент до 1200–1320 px, адаптивные отступы и сетки.
- Компоненты первого этапа: `Header`, `Footer`, `SectionHeader`, `CTASection`, `PainCard`, `SolutionCard`, `MetricCard`, `RadarAlert`, `RadarWidget`, `FlowDiagram`, `DashboardFrame`. Реализуются только действительно используемые на главной.
- Схемы строятся HTML/SVG/CSS. Видимое состояние hover/focus, клавиатурная навигация, семантические заголовки, мобильное меню.

## 5. Техническая реализация и приёмка

- Подготовить Vite + React + TypeScript strict, Tailwind CSS, React Router; Framer Motion и Lucide подключать только при необходимости.
- Вынести текстовые структуры и демо-данные в `src/data`, расчёт демо — в `src/lib`; держать интерактивное состояние в UI-компонентах. Отправку обращения позже подключать через отдельный интерфейс, без транспорта в компонентах.
- Добавить тесты для функциональности навигации, Radar и расчёта, а также проверку сборки так, чтобы каждый `build` запускал автотесты и проверку типов. При ошибке исправить причину и повторить сборку.
- Проверить desktop и mobile визуально, клавиатурное управление, `prefers-reduced-motion`, отсутствие ошибок консоли, корректность title/description/canonical/OpenGraph и загрузки ресурсов. Цели Lighthouse из ТЗ: более 90 по Performance, Accessibility, SEO и Best Practices.
- Подготовить production Dockerfile (Node build → nginx, SPA fallback), но не развёртывать без отдельной задачи.
- После визуального согласования главной распространить дизайн-систему на остальные страницы отдельными этапами.
